# LaTeX 渲染卡顿优化计划

> 起于 2026-10-03。分析结论见对话记录，本文件是**执行计划与进度**。

## 一、瓶颈假设（已对代码核实）

| 环节 | 假设 | 性质 |
|---|---|---|
| 资源准备 | 首次创建排版引擎 + 页面就绪等待，单次可达 20s | 已确认 |
| 排版计算 | 批量接口整体跑在主线程，含长卷分配、整屏 draw、逐条切片 | 已确认 |
| 绘制显示 | 抓图后做**全像素逐点统计**，只为判「是否全空白」 | 已确认 |
| 重复渲染 | 流式期间 `mathKeys` 每 500ms 变一次 → 整篇 Markdown 重解析 + 全量重渲染 | 已确认 |
| 列表滚动 | `RichText` 无可见性判断，屏幕外条目照样排版 | 已确认 |
| 交互调度 | 多个富文本实例争抢同一把互斥锁；失败重试在上游繁忙时放大占用 | 已确认 |
| 单条路径 | 每条 2 次帧等待 + 一张视口大小临时图 + 2 次整屏 draw + 全像素统计 + 一条日志 | 已确认 |

**关键观察**：缓存是按字节计的 `LruCache`，机制本身没问题。但**重组路径没有走缓存就直接重解析重提交**——
所以成本大头很可能不在「渲染」，而在渲染之外的开销。

**最坏情况量化**：长卷上限 `2048 × 4096` = 33.5 MB 一张；全像素统计按每批 6 条公式算，
最坏一次抓图要 838 万次 JNI 调用。

## 三、硬性约束

1. **零新增依赖**。不用任何新的图片库、排版库、协程库。
2. **每条修复必须写回归测试，并做变异验证**（把 bug 放回去看是否变红）。
   光有测试不算数——本项目已多次被「测试全绿但测试没跑」骗过。
3. **Bitmap 在 JVM 单测里是空壳**，所以涉及像素的判定逻辑必须留出可注入的接缝，
   测试用假采样器驱动，**不许复制一份实现到测试里**。
4. **单条与批量两条路径都要改**。只改一条等于没改——用户走的是不同入口。
5. 中文提交信息；界面文案集中在 `strings.xml`。

## 四、进度日志

### 2026-10-03 P0-1 完成

**问题**：`capture()` 与 `captureSheet()` 在每次抓图后都调用 `alphaStats(bitmap)`——
对整张位图逐点 `getPixel`，只为了判断「是不是全透明」。
长卷最坏 838 万次 JNI 调用，**发生在主线程上**。另有每次抓图一条 `Log.i`，
里面还把 AlphaInfo 全字段拼成字符串。

**改法**：
- 抽出 `isBlankBySampling(width, height, alphaAt)`：网格采样，判定「有没有可见像素」。
  注入 `alphaAt` 接缝使它可单测。
- `alphaStats` **保留**，但只供 `diagnose()` 排障用——不删诊断能力，
  只是不让它一直付费。
- 去掉常规路径上的 `Log.i`。

**取舍（必须诚实记下）**：采样理论上可能漏掉极细的内容。
用 48×48 网格（最多 2304 点）换 838 万点，量级上降三个数量级。
公式框尺寸由 JS 量得、内容占比高，漏判概率低；但这确实是用一点理论精度换性能。
若真机上出现「公式被判空白而不显示」，应先调密网格，而不是把全像素统计放回去。

**变异验证**：把采样改回逐点全扫描后重跑，测试必须变红。
